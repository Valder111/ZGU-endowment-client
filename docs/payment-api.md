# Подключение пожертвований

Клиент подключён к checkout серверной ветки `payment-system` и изменениям `origin/main` из коммита `d27dfa5` (18.11.2026): собранная сумма проекта и ручные пополнения. Проверены роутер, обработчики, права, сервисы, репозитории, миграция и Swagger. Клиентская интеграция не изменяет серверный исходный код и не выполняет миграции. Автоматические проверки не создают настоящих банковских заказов.

## Адреса и сборка

- Оформление: `/donate/`.
- Результат: `/donate/success/`, `/donate/failure/`.
- Совместимые адреса возврата из серверной конфигурации: `/payment/success/`, `/payment/fail/`.
- Статистика: `/admin/` → «Пожертвования» (администратор).

`VITE_API_BASE_URL=/api/v1` направляет запросы через nginx клиента; `API_UPSTREAM` задаёт существующий сервер. Для разработки: `STAFF_API_PROXY_TARGET=http://127.0.0.1:8080`. Абсолютный HTTPS-адрес API тоже поддерживается, но междоменные сессии требуют соответствующей настройки сервера.

Checkout включён при заданном корректном API, если `VITE_PAYMENTS_ENABLED` не равен `false`. Это переменная **сборки**: после изменения нужно пересобрать клиент. `VITE_PAYMENTS_SANDBOX=true` дополнительно разрешает адрес `https://test.best2pay.net`; в рабочем режиме разрешён только `https://pay.best2pay.net`. Платёжные секреты находятся исключительно на сервере.

## Реальные запросы

Все пути ниже относительны к `VITE_API_BASE_URL`.

| Запрос                                            | Назначение и доступ                                                                                                      |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `GET /projects`                                   | Открытые проекты, их UUID, валюта, статус и целевая сумма. Форма допускает только `published` и `RUB`.                   |
| `POST /payments/checkout`                         | Публичное создание банковского заказа, карта или СБП. Возвращает `payment_id`, `donation_id`, `order_id`, `payment_url`. |
| `GET /payments`, `GET /donations`, `GET /refunds` | Закрытые списки для сотрудников. Из них клиент собирает статистику; контакты жертвователей в интерфейс не выводятся.     |
| `GET /payments/{id}`                              | Только сотрудникам. Проверка статуса конкретного платежа.                                                                |
| `POST /payments/{id}/sync`                        | Сверка с банком по кнопке «Сверить» в админке; после ответа списки перечитываются.                                       |

Пример тела checkout (UUID должны существовать или быть сгенерированы для ключа):

```json
{
  "project_id": "<UUID опубликованного проекта>",
  "amount": "2500.00",
  "currency": "RUB",
  "method": "card",
  "idempotency_key": "<случайный UUID попытки>",
  "is_anonymous": true,
  "donor_email": "donor@example.org",
  "offer_version": "text-sha256:<SHA-256 текста оферты>",
  "offer_accepted_at": "<ISO 8601: момент согласия>"
}
```

Сумма в API — **строка рублей с десятичной точкой**, не копейки. Внутри клиента расчёты выполняются в целых копейках. Форма принимает только целые рубли от **10 ₽**, автоматически группирует цифры точками. В окне пожертвования и на странице оформления доступны только разовые платежи. Прежний параметр `mode=recurring` игнорируется: старая ссылка открывает обычную форму с сохранёнными суммой и направлением. Email необязателен и передаётся только после отдельного согласия. Клиент не собирает реквизиты карты. Хеш оферты обозначает версию показанного текста и не подменяет реквизиты утверждения документа.

Повторная отправка неизменённой формы после ошибки сохраняет `idempotency_key` и момент принятия оферты. Изменение данных создаёт новую попытку. Защита от двойного клика работает до перехода в банк. Тайм-аут checkout — 75 секунд: сервер сам обращается к процессингу. В текущем сервере срок жизни банковского заказа — 5 минут.

При временном ответе шлюза 502/504 либо серверном 503 с точным сообщением «Платёжный сервис недоступен» клиент один раз повторяет запрос через 600 мс. Тело, ключ попытки и момент согласия остаются теми же. Если повтор также завершился ошибкой, форма предлагает повторную отправку вручную. Ошибки настройки сервиса, проверки подписи и валидации автоматически не повторяются; при уходе со страницы запрос отменяется. Это смягчает временные обрывы соединения сервера с процессингом, но не устраняет сетевую причину на стороне этого соединения.

Для СБП отправляется `method: "sbp"`, затем открывается размещённая у процессинга страница. `authorize` (блокировка без списания), возврат, завершение авторизации и управление кассами не выполняются интерфейсом пожертвования.

## Связь направлений и проектов

Все пять направлений и все открытые проекты ведут в один общий рублёвый сбор. Выбранное название остаётся в форме и в обращении по почте как контекст участия, но в checkout отправляется только UUID общего проекта. На страницах проектов кнопка «Поддержать проект» использует ту же привязку.

По умолчанию используется опубликованный проект «Общее развитие университета "ЗГУ"» рабочего сайта: `37da0b64-1ed8-4a85-92df-3fcd7b413475`. Переменная сборки `VITE_DONATION_PROJECT_MAP` позволяет переопределить только `fund` для другой базы: `{"fund":"<UUID общего проекта>"}`. Прежние индивидуальные привязки `direction:*` не применяются. Значение `project:<UUID>` в URL сохраняет выбор в интерфейсе и не переключает получателя платежа на другой сбор.

Клиент проверяет, что общий проект есть в публичной выдаче, опубликован и имеет валюту RUB. Если его нет, платёж не создаётся; другой проект вместо него не подставляется. Локальный проект «ывыв» больше не используется настройкой `.env`. Для проверки с рабочими данными API клиента должен указывать на рабочую базу; в локальной базе нужного UUID может не быть.

## Общие показатели сбора

Главная, юбилейная страница, каталог направлений, страницы направлений, карточки и страницы опубликованных проектов используют одну запись общего проекта из публичного `GET /projects`. Обновление — раз в 20 секунд и при возвращении к вкладке.

- `target_amount` — цель в рублях; также поддерживается поле `amount` как альтернативное название цели.
- `current_amount` — собранная сумма в рублях по актуальному контракту. Сервер сам учитывает подтверждённые пожертвования, завершённые возвраты и ручные пополнения; клиент не прибавляет их повторно. Прежнее `total` поддерживается только при отсутствии `current_amount`. Поддерживаются денежная строка и числовое значение; нулевая сумма сохраняется как ноль.
- Значения приводятся к целым копейкам перед расчётом прогресса. Все ключи `fund`, `direction:*` и `project:*` указывают на один объект итогов.
- Цели и суммы других проектов не подменяют общие показатели. Отсутствующее или некорректное значение не превращается в ноль: выводится «—». Приватные платежи, пожертвования и возвраты для публичного прогресса не запрашиваются.

`current_amount` возвращается в публичных списке и карточке проекта после обновления сервера до нового коммита. При проверке рабочего сайта 18.11.2026 развёрнутая версия ещё не возвращала это поле. Если ни `current_amount`, ни прежнего `total` нет, выводится «—»; это не нулевая собранная сумма. Ранее опубликованные 2 020 000 ₽ остаются резервным значением статической версии/ошибки загрузки. Обновление клиента не меняет серверные финансовые записи.

## Ручные пополнения

В редакции откройте «Проекты», затем существующий проект. Под формой доступен раздел «Ручные пополнения» с серверным балансом, историей, суммами, комментариями и датами в часовом поясе Норильска.

- `GET /projects/{id}/adjustments` — список, доступен admin и moderator.
- `POST /projects/{id}/adjustments` — только admin, тело `{ "amount": "10000.50", "comment": "Платёжное поручение № 42" }`. Сумма положительная, от 0,01, до двух знаков копеек; комментарий обязателен, до 2000 символов.
- `DELETE /projects/{id}/adjustments/{adjustmentId}` — только admin, после подтверждения. Сервер логически удаляет запись и вычитает её сумму из `current_amount`; повтор не уменьшает баланс ещё раз.

Пополнения сохраняются только по кнопке, автосохранения финансовых записей нет. После успешной операции перечитываются история и баланс с сервера; оптимистического изменения суммы нет. Раздел обновляется раз в 30 секунд и при возвращении к вкладке. Черновик суммы и комментария сохраняется в состоянии формы при обновлении. При неоднозначной ошибке сохранения история перечитывается, автоматического повторного POST нет. Модератору элементы изменения не показываются; сервер независимо проверяет права. Старый API показывает ошибку загрузки с повторной попыткой, не поддельную пустую историю.

Ручные пополнения учитывают уже полученные переводы вне сайта. Они не создают банковскую транзакцию и не подменяют онлайн-платежи в платёжном реестре. У каждого проекта администратор видит его фактический баланс; публичные направления и checkout по принятой настройке используют общий проект фонда.

## Результат и ограничения существующего сервера

Адрес возврата банка выбирает экран для посетителя: `/payment/success/` и `/donate/success/` показывают «Оплата прошла успешно», `/payment/fail/` и `/donate/failure/` — «Платёж не прошёл». Это отображение результата возврата, а не подтверждение поступления денег в базе. Параметр `status` в URL игнорируется.

Для показа результата нужен номер заказа/UUID платежа в ссылке или сохранённая попытка checkout в той же вкладке. Если номер заказа или UUID противоречит сохранённой попытке, экран сообщает, что платёж определить не удалось. Открытие success/fail без реквизитов и сохранённой попытки не показывает успешную оплату.

В текущем сервере **нет публичной ручки статуса отдельного платежа**. Все списки пожертвований, платежей и возвратов требуют сессии сотрудника; публичный баланс доступен в `current_amount` проекта. Поэтому:

- Обычный посетитель сразу видит экран успеха/неудачи по адресу возврата Best2Pay и номер заказа для обращения в фонд. На успешном экране поясняется, что подтверждение поступит фонду от банка; полученная сумма без ответа API не утверждается. Клиент не запрашивает закрытые списки и не меняет финансовые записи по URL.
- Сотруднику с активной сессией доступна проверка конкретного платежа каждые 4 секунды до окончательного статуса. При 401/403 проверки прекращаются. Подтверждённый API результат имеет приоритет над адресом возврата: `paid` показывает «Пожертвование принято» и сумму, `failed/cancelled` — отказ. Пока ответ не получен или остаётся `pending`, отображается экран по адресу возврата.
- Публичные показатели обновляются из общего проекта раз в 20 секунд: цель — `target_amount`/`amount`, собрано — `current_amount` (с совместимостью для `total`). Если собранная сумма отсутствует, отображается «—» с пояснением.
- Переходы браузера не увеличивают сумму фонда. Данные API имеют приоритет над ранее опубликованной суммой **2 020 000 ₽**.

Показ экранов успеха/неудачи после возврата реализован на клиенте и не требует нового API. Живой прогресс использует серверный `current_amount`; для проверки статуса отдельного платежа обычным посетителем по-прежнему нужна отдельная безопасная ручка. Backend в рамках данной задачи не менялся.

В sessionStorage сохраняется только номер заказа, UUID платежа/пожертвования, сумма и время начала — для сопоставления возврата в той же вкладке. Email и данные карты там не сохраняются. Если хранилище недоступно, можно уточнить результат у фонда по номеру, который вернул банк.

## Статистика сотрудников

Списки перечитываются каждые 30 секунд и по кнопке «Обновить». Периоды 3/6/12 календарных месяцев включают текущий, часовой пояс — `Asia/Krasnoyarsk` (Норильск). Поступления относятся к месяцу `paid_at`; завершённые возвраты — к месяцу `completed_at`. Платёж с сохранённым `paid_at` учитывается в валовом поступлении даже после отмены, а возврат вычитается отдельно. Возвраты `pending/failed` и неоплаченные операции в поступления не входят. Возврат по платежу без `paid_at` также не вычитается из поступлений: отмена блокировки ещё не означает возврат списанных денег. Повторные записи по UUID не удваивают итог. Другие валюты исключаются из рублёвых итогов.

Показываются валовые поступления за месяц, сумма за период с учётом возвратов, возвраты и количество оплаченных платежей. Нетто за короткий период может быть отрицательным, если в нём вернули оплату предыдущего периода. График сравнивает поступления и возвраты; нажатие на месяц отбирает соответствующие платежи. Отдельная диаграмма показывает распределение операций по статусам. Средний и крупнейший вклады рассчитаны по операциям с подтверждённым списанием.

Реестр имеет поиск по названию/UUID проекта, номеру заказа банка, UUID платежа и пожертвования; фильтр статуса и страницы по 10 записей. Карточка операции показывает полные идентификаторы, даты и сверку с банком. Проект определяется только по связи `payment.donation_id → donation.project_id → project.id`. При отсутствии связи выводится «Проект не найден», другой проект вместо него не подставляется. Новые платежи всех направлений и открытых проектов относятся к общему сбору. Исторические записи показывают фактическую связь, сохранённую сервером. Отмена операций и создание возвратов в интерфейс не добавлены.

На телефоне строки реестра отображаются карточками, график прокручивается внутри своей области. Сервер пока отдаёт полные списки без пагинации, поэтому при большом объёме потребуется агрегирующий API.

## Состояние окружения и проверка

Новый коммит `d27dfa5` находится в серверной `origin/main`, а локальная `payment-system` остаётся на `fd4ab36`. В `main` есть `current_amount` и ручные пополнения, но ещё нет checkout и sync из платёжной ветки. Для полной проверки нужен сервер, объединяющий обе возможности. Клиентская кодогенерация объединяет спецификации без переключения или изменения серверной рабочей копии: см. [CODEGEN.md](CODEGEN.md). При проверке 18.11.2026 текущие локальный и рабочий API ещё не отдавали `current_amount`; клиентское обновление само не развёртывает новый backend.

Банк не может доставить уведомление на `127.0.0.1` пользователя. Поэтому локальная запись может оставаться `pending` после фактической оплаты: «Обновить» перечитывает базу, а «Сверить» запрашивает банк и обновляет серверную запись. В ходе диагностики сверка существующих заказов подтвердила две оплаты по 100 ₽; новые списания не запускались. Для автоматического получения уведомлений при размещении нужен доступный банку адрес callback из серверной конфигурации. Переход на success/fail не заменяет эту проверку.

Интеграционные проверки подменяют HTTP-ответы точным контрактом из сервера и не создают настоящих заказов:

```powershell
$env:VITE_API_BASE_URL = '/api/v1'
$env:VITE_PAYMENTS_ENABLED = 'true'
npm run build
npx playwright test tests/payments.spec.ts
```

Кодогенерация только клиента: `npm run gen:api`. Подробнее — [CODEGEN.md](CODEGEN.md).
