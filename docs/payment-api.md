# Подключение пожертвований

Клиент подключён к контракту локальной серверной ветки `payment-system`, проверенному 18.11.2026 по роутеру, обработчикам, сервисам и Swagger. Клиентская интеграция не изменяет серверный исходный код и не выполняет миграции. Автоматические проверки не создают настоящих банковских заказов.

## Адреса и сборка

- Оформление: `/donate/`.
- Результат: `/donate/success/`, `/donate/failure/`.
- Совместимые адреса возврата из серверной конфигурации: `/payment/success/`, `/payment/fail/`.
- Статистика: `/admin/` → «Пожертвования» (администратор).

`VITE_API_BASE_URL=/api/v1` направляет запросы через nginx клиента; `API_UPSTREAM` задаёт существующий сервер. Для разработки: `STAFF_API_PROXY_TARGET=http://127.0.0.1:8080`. Абсолютный HTTPS-адрес API тоже поддерживается, но междоменные сессии требуют соответствующей настройки сервера.

Checkout включён при заданном корректном API, если `VITE_PAYMENTS_ENABLED` не равен `false`. Это переменная **сборки**: после изменения нужно пересобрать клиент. `VITE_PAYMENTS_SANDBOX=true` дополнительно разрешает адрес `https://test.best2pay.net`; в рабочем режиме разрешён только `https://pay.best2pay.net`. Платёжные секреты находятся исключительно на сервере.

## Реальные запросы

Все пути ниже относительны к `VITE_API_BASE_URL`.

| Запрос                                            | Назначение и доступ                                                                                                      |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `GET /projects`                                   | Открытые проекты, их UUID, валюта, статус и целевая сумма. Форма допускает только `published` и `RUB`.                   |
| `POST /payments/checkout`                         | Публичное создание банковского заказа, карта или СБП. Возвращает `payment_id`, `donation_id`, `order_id`, `payment_url`. |
| `GET /payments`, `GET /donations`, `GET /refunds` | Закрытые списки для сотрудников. Из них клиент собирает статистику; контакты жертвователей в интерфейс не выводятся.     |
| `GET /payments/{id}`                              | Только сотрудникам. Проверка статуса конкретного платежа.                                                                |
| `POST /payments/{id}/sync`                        | Сверка с банком по кнопке «Сверить» в админке; после ответа списки перечитываются.                                       |

Пример тела checkout (UUID должны существовать или быть сгенерированы для ключа):

```json
{
  "project_id": "<UUID опубликованного проекта>",
  "amount": "2500.00",
  "currency": "RUB",
  "method": "card",
  "idempotency_key": "<случайный UUID попытки>",
  "is_anonymous": true,
  "donor_email": "donor@example.org",
  "offer_version": "text-sha256:<SHA-256 текста оферты>",
  "offer_accepted_at": "<ISO 8601: момент согласия>"
}
```

Сумма в API — **строка рублей с десятичной точкой**, не копейки. Внутри клиента расчёты выполняются в целых копейках. Форма принимает только целые рубли от **100 ₽**, автоматически группирует цифры точками. Email необязателен и передаётся только после отдельного согласия. Клиент не собирает реквизиты карты. Хеш оферты обозначает версию показанного текста и не подменяет реквизиты утверждения документа.

Повторная отправка неизменённой формы после ошибки сохраняет `idempotency_key` и момент принятия оферты. Изменение данных создаёт новую попытку. Защита от двойного клика работает до перехода в банк. Тайм-аут checkout — 75 секунд: сервер сам обращается к процессингу. В текущем сервере срок жизни банковского заказа — 5 минут.

При временном ответе шлюза 502/504 либо серверном 503 с точным сообщением «Платёжный сервис недоступен» клиент один раз повторяет запрос через 600 мс. Тело, ключ попытки и момент согласия остаются теми же. Если повтор также завершился ошибкой, форма предлагает повторную отправку вручную. Ошибки настройки сервиса, проверки подписи и валидации автоматически не повторяются; при уходе со страницы запрос отменяется. Это смягчает временные обрывы соединения сервера с процессингом, но не устраняет сетевую причину на стороне этого соединения.

Для СБП отправляется `method: "sbp"`, затем открывается размещённая у процессинга страница. `authorize` (блокировка без списания), возврат, завершение авторизации и управление кассами не выполняются интерфейсом пожертвования.

## Связь направлений и проектов

На странице оплаты и в окне пожертвования доступны одни и те же пять направлений. Выбор из окна сохраняется при переходе и отображается в итогах формы. Статические направления сайта (`direction:science`, `direction:students` и другие), а также `fund` не являются UUID проектов. Прямая ссылка `/donate/?target=project:<UUID>` выбирает соответствующий проект.

В обоих списках после направлений отображается группа «Проекты фонда» с опубликованными рублёвыми проектами из API, включая проект общего сбора. При выборе проекта сохраняются его UUID и название; платёж относится к выбранному проекту. Связь пяти основных направлений с общим сбором продолжает действовать независимо от этого списка.

Связь задаёт переменная сборки `VITE_DONATION_PROJECT_MAP`: JSON-объект, где ключи — `fund` или `direction:science` и т. п., значения — действительные UUID. По решению фонда все пять направлений ведут в один общий сбор: достаточно `{"fund":"<UUID общего сбора>"}`. Это значение используется для направлений без отдельной настройки. Индивидуальный ключ направления имеет приоритет. Выбранное направление остаётся в форме, а в API отправляется UUID общего сбора; отдельный учёт направления серверным контрактом не предусмотрен.

Клиент проверяет наличие, публикацию и валюту связанного проекта по API. При недоступном связанном сборе форма показывает причину и переводит фокус к выбору. Можно явно выбрать другой опубликованный рублёвый проект из раздела «Проекты фонда». Первый попавшийся проект не выбирается автоматически; записи на сервере не создаются. Без опубликованных рублёвых проектов кнопка оплаты недоступна. Локальная настройка общего сбора находится в игнорируемом Git файле клиента `.env`; для размещения на другом сервере нужно задать его действительный UUID в окружении сборки.

## Результат и ограничения существующего сервера

Адрес возврата банка выбирает экран для посетителя: `/payment/success/` и `/donate/success/` показывают «Оплата прошла успешно», `/payment/fail/` и `/donate/failure/` — «Платёж не прошёл». Это отображение результата возврата, а не подтверждение поступления денег в базе. Параметр `status` в URL игнорируется.

Для показа результата нужен номер заказа/UUID платежа в ссылке или сохранённая попытка checkout в той же вкладке. Если номер заказа или UUID противоречит сохранённой попытке, экран сообщает, что платёж определить не удалось. Открытие success/fail без реквизитов и сохранённой попытки не показывает успешную оплату.

В текущем сервере **нет публичной ручки статуса платежа и нет публичных агрегатов поступлений**. Все списки пожертвований, платежей и возвратов требуют сессии сотрудника. Поэтому:

- Обычный посетитель сразу видит экран успеха/неудачи по адресу возврата Best2Pay и номер заказа для обращения в фонд. На успешном экране поясняется, что подтверждение поступит фонду от банка; полученная сумма без ответа API не утверждается. Клиент не запрашивает закрытые списки и не меняет финансовые записи по URL.
- Сотруднику с активной сессией доступна проверка конкретного платежа каждые 4 секунды до окончательного статуса. При 401/403 проверки прекращаются. Подтверждённый API результат имеет приоритет над адресом возврата: `paid` показывает «Пожертвование принято» и сумму, `failed/cancelled` — отказ. Пока ответ не получен или остаётся `pending`, отображается экран по адресу возврата.
- Из публичных проектов обновляются целевые суммы (раз в 20 секунд). Собранная сумма по проектам не выдумывается и не заменяется нулём; показывается «—» с пояснением.
- Общая опубликованная сумма фонда остаётся **2 020 000 ₽**. Автоматически увеличивать её по переходам браузера нельзя.

Показ экранов успеха/неудачи после возврата реализован на клиенте и не требует нового API. Полноценное публичное подтверждение поступления из базы и живой прогресс поступлений потребуют публичных безопасных ответов от API. Backend в рамках данной задачи не менялся.

В sessionStorage сохраняется только номер заказа, UUID платежа/пожертвования, сумма и время начала — для сопоставления возврата в той же вкладке. Email и данные карты там не сохраняются. Если хранилище недоступно, можно уточнить результат у фонда по номеру, который вернул банк.

## Статистика сотрудников

Списки перечитываются каждые 30 секунд и по кнопке «Обновить». Периоды 3/6/12 календарных месяцев включают текущий, часовой пояс — `Asia/Krasnoyarsk` (Норильск). Поступления относятся к месяцу `paid_at`; завершённые возвраты — к месяцу `completed_at`. Платёж с сохранённым `paid_at` учитывается в валовом поступлении даже после отмены, а возврат вычитается отдельно. Возвраты `pending/failed` и неоплаченные операции в поступления не входят. Возврат по платежу без `paid_at` также не вычитается из поступлений: отмена блокировки ещё не означает возврат списанных денег. Повторные записи по UUID не удваивают итог. Другие валюты исключаются из рублёвых итогов.

Показываются валовые поступления за месяц, сумма за период с учётом возвратов, возвраты и количество оплаченных платежей. Нетто за короткий период может быть отрицательным, если в нём вернули оплату предыдущего периода. График сравнивает поступления и возвраты; нажатие на месяц отбирает соответствующие платежи. Отдельная диаграмма показывает распределение операций по статусам. Средний и крупнейший вклады рассчитаны по операциям с подтверждённым списанием.

Реестр имеет поиск по названию/UUID проекта, номеру заказа банка, UUID платежа и пожертвования; фильтр статуса и страницы по 10 записей. Карточка операции показывает полные идентификаторы, даты и сверку с банком. Проект определяется только по связи `payment.donation_id → donation.project_id → project.id`. При отсутствии связи выводится «Проект не найден», другой проект вместо него не подставляется. Пять направлений сайта используют настроенный общий сбор; явно выбранный отдельный проект сохраняет собственный UUID. Поясняющая плашка об общем сборе убрана. Отмена операций и создание возвратов в интерфейс не добавлены.

На телефоне строки реестра отображаются карточками, график прокручивается внутри своей области. Сервер пока отдаёт полные списки без пагинации, поэтому при большом объёме потребуется агрегирующий API.

## Состояние окружения и проверка

При первоначальной проверке 18.11.2026 локальный API был недоступен, а на рабочем сайте новый checkout возвращал 404. После запуска локального сервера доступны `127.0.0.1:8080` и клиент `127.0.0.1:5181`. Это не подтверждает обновление рабочего сайта: размещённая версия должна отдельно использовать актуальный платёжный API.

Банк не может доставить уведомление на `127.0.0.1` пользователя. Поэтому локальная запись может оставаться `pending` после фактической оплаты: «Обновить» перечитывает базу, а «Сверить» запрашивает банк и обновляет серверную запись. В ходе диагностики сверка существующих заказов подтвердила две оплаты по 100 ₽; новые списания не запускались. Для автоматического получения уведомлений при размещении нужен доступный банку адрес callback из серверной конфигурации. Переход на success/fail не заменяет эту проверку.

Интеграционные проверки подменяют HTTP-ответы точным контрактом из сервера и не создают настоящих заказов:

```powershell
$env:VITE_API_BASE_URL = '/api/v1'
$env:VITE_PAYMENTS_ENABLED = 'true'
npm run build
npx playwright test tests/payments.spec.ts
```

Кодогенерация только клиента: `npm run gen:api`. Подробнее — [CODEGEN.md](CODEGEN.md).
